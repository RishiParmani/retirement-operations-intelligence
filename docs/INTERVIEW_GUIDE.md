# Interview Guide - ROIP

Everything below is grounded in what this repo actually does. Where something was **not** done or not verified, the answer says so; say the same in an interview. Numbers are from `reports/`.

## Explanations to memorise

**30 seconds.** "ROIP is a portfolio project on synthetic retirement-operations data. I built a validated pipeline, a SQL layer, KPI and root-cause analysis, an SLA-breach model and a five-page Power BI dashboard. The main finding is that exceptions and missing intake information are the strongest drivers of SLA breaches, while team, region and channel make no practical difference."

**1 minute.** Add: "The pipeline takes 200,600 raw records, rejects 1,400 with a rule id and reason, fixes or flags the rest, and checks raw equals clean plus rejected. KPI definitions live in one place and a test proves SQL and Python agree: SLA compliance 73.3%, mean processing time 37.3 hours. I audited my own earlier model too: it used features not known at intake and a random split, so I rebuilt it with a time-based split and baselines. It adds only modest value over a simple rate table, and I say that."

**2 minutes.** Add the business side: "Breach rate is 61% with an exception vs 23% without, and 66% when intake information is missing vs 24%. Missing information also raises the exception rate from 8% to 50%, so fixing intake completeness is upstream of both. Workload above 95 is a third of work but 41% of breaches. I'd recommend intake validation, an exception owner with a time-box, and a workload cap. Caveat: the data is synthetic and these relationships were built into the generator, so the value is the method, not the numbers."

**Technical walk-through.** `data_generation.py` (seeded) -> `etl.py` with `dq.py` (reject / fix / flag stages, issue log, before/after profile, logging, row-accounting assert) -> clean CSV loaded by DuckDB/PostgreSQL and Power BI -> `kpis.py` as the KPI source of truth -> `analysis.py` (Cramér's V effect sizes, excess-breach attribution, backlog age) -> `modeling.py` (staged feature sets, leakage guard, temporal split, logistic regression vs gradient boosting vs rate tables) -> PBIP generated by Python scripts so the dashboard is reviewable text in Git.

## Business

**Q: What problem does this solve?** *A:* It tells an operations manager where SLAs are being missed and what is associated with it, so they can act on intake quality, exceptions and workload instead of blaming teams. *Reasoning:* breaches are 26.7% of completed work; most sit in identifiable, fixable segments. *Follow-ups:* "Who is the audience?" (ops managers and an executive summary page); "What would you do first?" (intake validation).

**Q: What are your top recommendations?** *A:* (1) Check completeness at intake. (2) Give exceptions a dedicated owner and time-box. (3) Cap workload around 95. (4) Review Medium/Low priority ageing. *Reasoning:* the first two attack the strongest drivers (V 0.21 and 0.26). *Follow-up:* "How would you measure success?" Breach rate for information-missing items and exception rate, tracked monthly.

**Q: Is the finding that Low priority breaches most a problem?** *A:* In this data Low is 37.9% vs Critical 10.5%. I'd treat it as something to investigate, not conclude: it comes from a duration multiplier in the generator, and in a real operation I'd check whether Low items simply wait longer by design. *Follow-up:* "What data would you want?" Queue wait time versus touch time.

**Q: Can you trust these numbers for real decisions?** *A:* No. The data is synthetic. I can defend the method: definitions, validation, reconciliation. The numbers illustrate it.

## Data

**Q: How did you handle data quality?** *A:* Three stages: reject (removed to a file with reason), fix (deterministic repair, logged), flag (kept and logged). On this data: 600 duplicate IDs and 800 invalid team values rejected, 1,594 missing regions set to `Unknown`, 2,748 `sla_breached` values re-derived, and flags such as 3,486 extreme processing times kept. *Reasoning:* dropping odd-but-real rows would bias volume. *Follow-ups:* "Why not drop outliers?" They are plausible long cases; I flag them. "How do you know nothing was lost?" `raw = clean + rejected` is asserted and tested.

**Q: Why do many rules show zero rows?** *A:* The defects the generator injects are duplicates, bad teams and missing regions. The other rules are guards, tested with injected bad rows. I'd not claim they found problems.

**Q: How did you define an SLA breach, and why Completed only?** *A:* `processing_hours > sla_target_hours` and status Completed. Pending/Failed/Escalated items did not finish, so their hours are not durations; 9,627 such rows have hours, flagged F08. The original dashboard computed compliance over all rows (wrong population); it gave 74.58%, not the reference 73.29%.

**Q: What is wrong with January 2026?** *A:* Nothing. No receipts after 31 Dec 2025, but 796 December receipts completed in January. It is run-off. I kept it and annotated it.

## Python

**Q: How is the code organised and tested?** *A:* Package `src/roip` with config, dq, etl, kpis, analysis, modeling, sqlrun; 28 pytest tests covering row accounting, determinism (byte-identical reruns), the SLA definition, KPI population rules on a toy frame, leakage guard, temporal split, SQL vs Python and the PBIP structure. *Follow-up:* "What isn't tested?" Plots, and DAX execution.

**Q: How do you compute effect sizes?** *A:* Chi-square based Cramér's V between each categorical dimension and breach. Thresholds (0.08 moderate, 0.20 strong) are my heuristic, not a standard. With 190k rows nearly everything is "statistically significant", so I rank by effect size.

**Q: What is the excess-breaches number?** *A:* Within each priority, how many fewer breaches there would be if flagged operations breached at the unflagged rate; e.g. about 7,464 for exceptions (14.7% of breaches). It is an association, and exception and missing-info shares overlap so they don't add.

## SQL

**Q: Walk me through a query you are proud of.** *A:* Q10 (driver scan): a CTE of completed operations with CASE-built levels, `UNION ALL` into one factor/level table, grouped with the overall rate from a scalar subquery to give lift. One query replaces eight. *Follow-up:* "Performance?" On 200k rows trivial; at scale I'd index `(status, sla_breached)` as in the schema.

**Q: Window functions you used?** *A:* LAG and running SUM for month-over-month (Q06), a 3-month moving breach rate with a window frame (Q07), RANK per partition (Q12, Q17), ROW_NUMBER top-N (Q19), cumulative share for Pareto (Q09, Q18).

**Q: How do you know SQL and Python agree?** *A:* DuckDB runs the SQL in a test and compares totals and rates to `kpis.py`. I did not run PostgreSQL; syntax is compatible apart from one DuckDB `DATE_DIFF`.

**Q: HAVING vs WHERE?** *A:* WHERE filters rows before grouping, HAVING filters groups after; Q03 and Q11 use HAVING to ignore tiny groups.

## Power BI

**Q: Describe the model.** *A:* One fact table, a Calendar with an active received-date relationship and an inactive completed-date one used via USERELATIONSHIP, plus two standalone DQ tables. 45 measures in display folders. *Why one fact table?* Single event table, low-cardinality attributes.

**Q: Why were KPI cards blank and did you fix it?** *A:* I could not reproduce it without Desktop, so the root cause is unconfirmed. I rewrote the two averages as SUM/COUNT with explicit formats and added a diagnostic panel to localise the failure quickly. I would not claim it is fixed until it renders in Desktop.

**Q: Card clipping?** *A:* Cards were 82 px tall and stacked title, 24 pt value and category label. I turned off the category label and reduced the font. Also needs a visual check.

**Q: Where does the DAX differ from the original?** *A:* The original SLA Compliance measure used all rows as the denominator (gave 74.58% instead of 73.29%). It now uses Completed only.

**Q: How would you handle row-level security or refresh?** *A:* Not implemented. For refresh I'd move from CSV to a database source and a gateway; RLS would need a real region/team ownership table.

## Analytics

**Q: Correlation vs causation here?** *A:* The generator causes the effects, so in this project I happen to know the truth; in real data I could only say "associated". I'd propose an intake-validation pilot with a control group.

**Q: Why does region not matter?** *A:* V = 0.007. Fits a generator that assigns region independently. In real data I'd still test, and I'd show sample sizes with every rate.

**Q: What would you add with more time?** *A:* Business-day SLA calendars, wait-vs-touch time, cost per operation, real data validation with the domain team.

## Machine learning

**Q: What did you find wrong in your original model?** *A:* It used `exception_flag` and `rework_flag`, which are only known during processing, while describing the features as operationally available; it used a random split; and it had no baseline. I rebuilt with three feature stages, a train Jan-Sep / test Oct-Dec split, baselines and calibration.

**Q: Results?** *A:* AUC 0.638 (intake), 0.677 (triage), 0.723 (in-flight); best rate-table baseline 0.648. Reviewing the top 20% of triage scores catches 35% of breaches at 46% precision vs 27% base rate. Gradient boosting matched logistic regression, so I recommend logistic regression with odds ratios (missing info: 7.0).

**Q: Is the model good enough to deploy?** *A:* No. The lift is modest, and a rate table gets most of it. I'd use it to rank a review queue at most, after checking calibration on real data. *Follow-up:* "When is ML not appropriate?" When a transparent rule gets nearly the same result and the data is small or unstable.

**Q: How did you prevent leakage?** *A:* Forbidden-column guard (`processing_hours`, `completed_at`, `sla_breached`), staged features by availability time, time-based split; tested.

**Q: Your recommended model's AUC (0.677) is lower than the old 0.715. Why?** *A:* The old number came from a random split and included in-flight features (exception, rework). The comparable figure is stage C at 0.723 on a harder time split. Stage B is lower because it only uses what is known at triage; that honesty is the point.

## Difficult questions

**Q: Isn't this just fake data?** *A:* Yes, by design, and the README says so. The project demonstrates definitions, validation, reconciliation and communication. I'd not present any number as a real-world finding.

**Q: What was your biggest mistake?** *A:* I had two tools disagree: Python averaged processing hours over all statuses while SQL used Completed only. Unifying them in `kpis.py` and testing it fixed that. Also my earlier docs wrongly said some financial rows had zero amount; it is exactly the four non-financial types, and I corrected it.

**Q: What did AI tools do in this project?** *A:* Be honest about your own role: you should be able to explain every file here. If you cannot, read the module before the interview. (This guide is written so you can.)

**Q: What would you not claim?** *A:* That the dashboard has been verified in Desktop v3, that any driver is causal, that the model should be deployed, or that PostgreSQL loading was tested.
